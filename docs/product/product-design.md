# 第一部分 调研与对比分析

## 二、调研对象与方法

本方案选取两个开源项目作为核心参考。调研通过项目 README、工具参考文档（TOOLS-REFERENCE.md）与机制参考文档（reference.md）完成，结论区分「已查证事实」与「参考观点」。

| 项目 | 定位 | 技术栈 | 许可 |
|------|------|--------|------|
| Pimzino/spec-workflow-mcp | 规格驱动开发（spec-driven）的 MCP 服务器，带实时 Web 仪表盘与 VSCode 扩展 | TypeScript / Node.js，MCP stdio + WebSocket | GPL-3.0 |
| yetone/magpie | 多 AI Agent 的模型、订阅与网关统一管理桌面应用 | Go + Wails v3 桌面壳 + Bun 插件运行时 + SQLite | MIT |

两个项目解决的问题不同但机制互补。spec-workflow-mcp 强在「任务状态机 + 实时可视化 + MCP 工具暴露」，magpie 强在「本机工具自动识别 + 多 Agent 适配写入 + 会话级追踪 + 多角色 MCP 集成」。这三点恰好覆盖本产品的三大核心命题。

## 三、spec-workflow-mcp 核心机制

### 3.1 架构形态

- 单一 MCP Server 进程，经 npx 分发，stdio transport 接入 AI 客户端。
- 独立 Web Dashboard（默认端口 5000），WebSocket 实时推送状态变更，多项目共用一个仪表盘实例。
- VSCode 扩展把仪表盘嵌入侧边栏，形成「MCP 工具 + 可视化面板」双入口。
- 状态落盘在用户项目的 `.spec-workflow/` 目录（specs、approvals、archive、steering、templates），文件即状态源。沙箱环境可用 `SPEC_WORKFLOW_HOME` 重定向。

### 3.2 工具识别方式

该项目不扫描本机安装的 AI 工具。其「工具识别」指两层含义：

1. MCP 协议自身的工具枚举。客户端连上 Server 后自动发现 13 个工具（create-spec-doc、spec-list、spec-status、manage-tasks、get-template-context、get-steering-context、get-spec-context、create-steering-doc、request-approval、get-approval-status、delete-approval 等）。
2. 对话内自然语言触发。用户提到 spec-workflow 关键词即路由到对应工具，例如「Create a spec for user authentication」。

### 3.3 任务状态管理（本产品最直接的借鉴点）

三层显式状态机，字段清晰可测：

| 层级 | 状态集合 | 说明 |
|------|----------|------|
| Spec 文档层 | not-created / pending-approval / approved / rejected / changes-requested | 按 requirements → design → tasks 顺序推进，审批未过不得进入下一阶段 |
| 任务层 | pending / in-progress / completed / blocked（附可选原因） | blocked 状态以 `_Blocked: reason_` 元数据写入 tasks.md，状态变更时自动清除 |
| 审批层 | pending / approved / rejected / changes-requested + 反馈文本 + 修订轮次 | 人机协同的 human-in-the-loop 节点，支持 revision 多轮 |

配套机制：审计日志（时间戳、操作者、动作、结果）、任务进度统计（total / completed / in-progress / pending）、实现日志与代码统计、WebSocket 实时同步。

### 3.4 MCP 集成方式

纯 MCP Server 角色。工具以 JSON Schema 声明参数，返回结构化结果（含 success / error / details / suggestion 错误三元组）。提供 10+ 客户端配置模板（Claude Code、Claude Desktop、Cursor、Cline、Continue、Windsurf、OpenCode、Codex、Augment 等），格式为各家的 mcpServers 配置。安全侧有 localhost 绑定、限流（120 req/min）、审计日志、安全响应头，TLS 与认证依赖反向代理补齐。

## 四、magpie 核心机制

### 4.1 架构形态

- 桌面应用（菜单栏 + 独立窗口 + TUI + Web UI + CLI 多形态）。
- 本地网关 `127.0.0.1:3425`，统一承接各 Agent 请求，向上翻译 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini 四种协议（含流式与工具调用），向下路由到 API Key、订阅账号或本地模型。
- 模块化内部结构：internal/agent（各 Agent 配置读写）、internal/gateway（协议转换与路由）、internal/provider、internal/pluginrt（Bun 插件运行时）、internal/sessions、internal/sqlitedb、internal/gui。

### 4.2 工具自动识别（本产品最直接的借鉴点）

三层探测机制，只展示已安装或已配置的 Agent：

| 探测层 | 方式 | 实例 |
|--------|------|------|
| 配置文件路径探测 | 按每个 Agent 的专属配置路径判断存在性，覆盖 macOS / Linux / Windows 与 XDG 规范，支持环境变量覆盖 | Claude Code 的 `~/.claude/settings.json`（CLADE_CONFIG_DIR 可覆盖）、Codex 的 `~/.codex/config.toml`、Zed 的 `~/.config/zed/settings.json` 等，适配表覆盖 60+ Agent |
| 可执行文件与进程探测 | 校验可执行文件版本或进程名，排除同名误判 | StepCode 严格目录制（`~/.stepcode`），避免误认同名 CLI；Reasonix 要求桌面安装或原生 Go CLI 版本号命中 |
| 运行时 API 探测 | 探测本地 API 端口判断运行中状态 | Alma 的 localhost:23001、OpenHanako 本地 API、OpenPencil 运行中拒绝写配置 |

配套能力：Agent 版本发现与升级提示、缺失 Agent 安装引导、订阅账号发现（读登录文件与 macOS Keychain，可隐私关闭）、模型列表从厂商 API 与 models.dev 补全。

### 4.3 配置读写与回滚

键级外科手术式编辑是关键工程细节。只改动用户指定的那个键，JSON/JSONC/TOML/YAML 的注释、键顺序、缩进完整保留，写入原子化。Disconnect 语义支持逐字节还原或选择性移除自身写入的键。部分 Agent 需重启生效，产品侧给出明确提示。项目级覆盖配置文件被识别但不修改。

### 4.4 会话与状态追踪

- Sessions 视图记录每个 Agent 会话的标题与成本，支持一键在终端重开。
- 会话文件回填。从 Claude Code、Claude Desktop、Codex、OpenCode 的会话文件读取调用记录，补全网关未捕获的行（如首 token 时间）。
- 会话粘性。路由组内同一会话绑定同一账号，保住厂商 prompt cache。
- 配额窗口跟踪。5 小时窗口、每周额度、pace 调度、窗口重置前提醒。
- Routing 视图实时展示每次路由决策，支持按 session ID 分组回放。

### 4.5 MCP 集成方式（三重角色）

| 角色 | 实现 |
|------|------|
| MCP Server | 对外暴露 web_search / web_fetch、图像与视频工具，任意 Agent 可挂载 |
| MCP Client 与桥接 | 驱动本地 claude 二进制，把 Agent 的工具经 MCP 桥接给订阅模型 |
| MCP 配置管理者 | Library 功能把用户写一次的 MCP server 配置，按各 Agent 自身格式写入其配置文件，卸载时只移除自身写入内容 |

## 五、三维对比与借鉴结论

### 5.1 三维对比表

| 对比维度 | spec-workflow-mcp | magpie | 对本产品的结论 |
|----------|-------------------|--------|----------------|
| 工具自动识别 | 不做本机扫描，依赖 MCP 协议枚举 + 对话触发 | 三层探测（配置路径 / 进程可执行 / 运行时 API），60+ Agent 适配表，版本与订阅发现 | 采用 magpie 式适配器注册表 + 三层探测；MCP 工具枚举作为补充通道 |
| 会话状态追踪 | 显式三层状态机（spec / task / approval），文件落盘 + WebSocket 实时推送，blocked 带原因 | 会话计量与回填（成本、配额、粘性、路由决策），无任务生命周期状态机 | 状态机设计借鉴 spec-workflow-mcp 并扩展为任务生命周期；会话溯源借鉴 magpie 的多源会话文件读取 |
| MCP 集成 | 纯 MCP Server，stdio，13 工具，多客户端配置模板 | 三重角色（Server / Client 桥接 / 配置管理者），协议双向翻译 | 双轨并行。自身以 MCP Server 暴露状态与控制工具；同时做 MCP Client 汇聚外部工具能力；提供多客户端一键接入配置 |
| 状态存储 | 项目内文件目录，人可读可 diff | SQLite + settings/plugins.yml 原子写 | 事件与状态用 SQLite（查询与统计），关键快照落 JSON 文件（可读可备份） |
| 实时性 | WebSocket 推送 | 网关实时路由视图 | 本地 UI 用 WebSocket 推送状态变更 |
| 安全 | localhost、限流、审计、Docker 加固 | 网关 Key、IP 白名单、TLS、代理头识别、隐私开关 | 全本地运行、默认不出网、扫描行为可关闭、审计日志必备 |

### 5.2 借鉴与差异点

1. 工具识别走适配器注册表模式。每个 AI 工具一个 Adapter 描述包，声明配置路径（含平台变体与环境变量覆盖）、进程名、可执行文件特征、运行时 API 端口、会话文件位置、状态事件提取方式。新增工具只加描述包，不改核心。
2. 状态机是产品骨架而非附属。spec-workflow-mcp 证明「显式状态 + 可见流转 + 人机审批节点」是 AI 开发工作流的刚需。本产品把状态机从「文档审批」扩展到「任务生命周期」，并把状态变更作为语音播报的一等触发源。
3. MCP 取双轨。只做 Server 会被动等调用，只做 Client 无法被 AI 工具发现。双轨使 AgentCue 既是「被管理对象的观察者」又是「可被 AI 工具调用的能力提供者」。
4. 会话溯源多源化。不同工具的会话证据链不同（CLI 的 JSONL 会话文件、IDE 的进程与窗口事件、MCP 的调用日志）。按工具适配器声明证据源，核心引擎统一归一为状态事件。
5. 反面约束。spec-workflow-mcp 维护停滞（作者暂离），提示我们适配器生态要可插拔、不绑死单一上游。magpie 不收 PR 的社区策略提示我们，若做开放生态需提前设计贡献协议与适配器校验器。

# 第二部分 产品设计方案

## 六、产品目标

### 6.1 背景与问题

多 AI 工具并用是当下开发者的常态。Claude Code、Cursor、Codex CLI、Gemini CLI、各类 MCP 工具各自为政，带来三个具体问题：

1. 工具分散不可见。本机装了哪些 AI 工具、版本如何、是否在运行、有哪些 MCP 服务挂载，缺少统一视图，靠人肉记忆。
2. 任务状态不可感。长任务跑在后台，「开始、等待人工确认、失败、完成」这些关键节点没有统一提示。人必须盯着终端或 IDE，或频繁切换窗口确认。等待人工介入的任务容易被漏掉，失败任务的发现滞后。
3. 外部工具集成碎片化。每个工具的 MCP 配置格式、会话文件格式、事件模型各不相同，跨工具汇聚状态与能力的成本高。

### 6.2 产品定位

AgentCue 是一款本地优先的 AI 工具工作流管理软件。它自动扫描识别本机已安装的 AI IDE 与开发工具，用统一的状态机管理各工具的任务生命周期，在关键状态变更时语音播报，并以 MCP 协议对外提供与汇聚工具能力。

一句话表述。看住本机所有 AI 工具的任务状态，在需要你的时候出声叫你。

### 6.3 目标用户

| 用户角色 | 特征 | 核心诉求 |
|----------|------|----------|
| 多工具开发者（主） | 同时使用 2 个以上 AI IDE 或编码 CLI，并行跑多个长任务 | 不漏掉「等确认」与「失败」，减少盯屏 |
| AI 工作流重度用户 | 用 MCP、子代理、长链路任务，单任务时长 10 分钟以上 | 任务生命周期可视化 + 提醒 |
| 工具/效率爱好者 | 乐于配置语音、快捷键、自动化规则 | 可定制的播报与规则引擎 |

画像说明。以上画像基于产品定位构建，属待验证假设，需在 M1 用 5 名目标用户访谈校准。

### 6.4 成功指标

| 指标 | 口径 | 目标值（MVP 后 3 个月） |
|------|------|------------------------|
| 工具识别覆盖率 | 识别出的已安装工具数 ÷ 用户实际在用工具数（抽样自查） | ≥ 90% |
| 关键状态漏报率 | 用户事后反馈「没听到/没看到」的关键事件数 ÷ 关键事件总数 | ≤ 2% |
| 播报打扰度 | 用户手动静音或关闭播报的周活跃用户占比 | ≤ 15% |
| 状态事件时延 | 工具产生状态事实到 AgentCue 呈现/播报的 P95 时延 | ≤ 3 秒 |
| 周活跃留存 | 安装后第 4 周仍每周至少触发 1 次状态播报的用户占比 | ≥ 35% |

口径说明。关键状态定义为「需要人工介入、执行失败、任务完成」三类。「任务开始」默认不播报，计入非关键。指标估算基于行业工具类产品常见水平，标注为估算，M1 后以实测替换。

### 6.5 需求范围

**本期包含**

1. 本机 AI 工具扫描识别与清单管理。
2. 任务生命周期状态机（四类关键节点 + 补充态）。
3. 状态变更语音播报（含规则、节流、免打扰）。
4. MCP 协议双向集成（自身 Server + 外部 Client 汇聚）。
5. 本地看板 UI（工具总览、会话状态、时间线、设置）。
6. 状态事件本地存储与检索。

**本期不包含**

1. 多机协同与云端同步（列入后续版本池）。
2. 团队席位、账号体系与计费。
3. AI 模型统一网关与模型路由（与 magpie 职责重叠，不做）。
4. 对工具任务的远程操控（如代点确认按钮）。本期只做「感知与提示」，不代操作。
5. 移动端 App。桌面系统通知 + 语音覆盖该场景。

## 七、核心功能模块

### 7.1 模块总览

| 模块编号 | 模块名 | 职责 | 优先级 |
|----------|--------|------|--------|
| MOD-1 | 工具扫描与识别引擎 | 发现本机 AI 工具，产出工具清单与能力画像 | Must |
| MOD-2 | 会话状态机引擎 | 归一多源事件为任务状态迁移，产出状态时间线 | Must |
| MOD-3 | 语音播报引擎 | 状态事件到语音输出的规则路由、队列与 TTS | Must |
| MOD-4 | MCP 集成层 | 自身 Server、外部 Client 汇聚、接入配置生成 | Must |
| MOD-5 | 会话看板 UI | 工具总览、状态卡、时间线、介入引导 | Must |
| MOD-6 | 设置与规则中心 | 播报规则、扫描范围、隐私开关、适配器管理 | Should |
| MOD-7 | 事件存储与检索 | SQLite 事件日志、查询、导出 | Should |
| MOD-8 | 适配器 SDK | 第三方工具适配器的开发规范与校验器 | Could（M3 起） |

### 7.2 MOD-1 工具扫描与识别引擎

**识别方式（三层探测，借鉴 magpie）**

| 探测层 | 用途 | 规则示例 |
|--------|------|----------|
| 配置文件探测 | 判定「已安装/已配置」 | 按适配器声明路径检测 `~/.claude/settings.json`、`~/.codex/config.toml`、`~/.cursor/` 等，支持平台路径变体与环境变量覆盖 |
| 进程与可执行探测 | 判定「运行中」与版本 | 按进程名/可执行文件特征匹配，排除同名误判；读取版本号 |
| 运行时 API 探测 | 判定「活跃会话」 | 探测工具本地 API 端口（如 127.0.0.1 段），获取会话数与运行状态 |

**功能需求**

| 编号 | 需求描述 | 业务规则 | 验收标准（Given/When/Then） |
|------|----------|----------|------------------------------|
| FR-01 | 自动扫描本机 AI IDE 与开发工具 | 首启自动执行，此后可手动触发或定时（默认 6 小时） | Given 本机装有 Claude Code，When 完成扫描，Then 工具清单出现 Claude Code 且标注版本与配置路径 |
| FR-02 | 适配器注册表驱动识别 | 每工具一个适配器描述包，声明配置路径、进程名、会话源、事件提取规则 | Given 注册表含 6 个适配器，When 扫描执行，Then 仅按适配器声明判定，不硬编码工具名于核心 |
| FR-03 | 工具状态标注 | 每个工具标注 已安装 / 运行中 / 未安装 / 未识别 四态 | Given 工具已安装未运行，When 查看清单，Then 状态显示「已安装」且运行指示为灰色 |
| FR-04 | 手动添加与忽略 | 用户可手动指定路径添加自定义工具，可忽略自动发现项 | Given 用户忽略某工具，When 再次扫描，Then 该项不出现（保留于「已忽略」分组可恢复） |
| FR-05 | 扫描隐私边界 | 扫描仅读取适配器声明的路径清单，不递归全盘，不上传任何内容 | Given 扫描完成，When 检查网络行为，Then 无任何出网请求（本地 TTS 除外） |

### 7.3 MOD-2 会话状态机引擎

**任务状态集合**

| 状态码 | 中文名 | 含义 | 允许的操作 |
|--------|--------|------|------------|
| idle | 待触发 | 任务已创建未开始 | 取消、编辑 |
| running | 执行中 | 任务开始，工具正在工作 | 取消、查看日志 |
| waiting_human | 待人工介入 | 需要用户确认、授权或补充输入 | 打开工具处理、取消、超时自动失败 |
| failed | 执行失败 | 工具报错或流程中断 | 重试、查看错误、归档 |
| completed | 任务完成 | 任务达成预期结果 | 查看结果、归档 |
| cancelled | 已取消 | 用户主动终止 | 归档、重新创建 |
| timeout | 超时无响应 | 心跳超时判定 | 重试、转失败、忽略 |

**状态迁移表**

| 当前态 | 触发事件 | 目标态 | 播报级别 |
|--------|----------|--------|----------|
| idle | task.started | running | 低（默认静默） |
| running | task.waiting_human | waiting_human | 高（可打断） |
| running | task.failed | failed | 高 |
| running | task.completed | completed | 中 |
| running | heartbeat.lost | timeout | 高 |
| waiting_human | human.responded | running | 低（默认静默） |
| waiting_human | task.timeout | timeout | 高 |
| failed / timeout | task.retried | running | 低 |
| completed / failed / cancelled / timeout | task.archived | idle | 无 |

约束规则：

1. 状态迁移单向可追溯，每次迁移写入事件日志（prev、next、trigger、actor、ts、reason）。
2. waiting_human 进入后启动介入倒计时（默认 30 分钟），超时迁移到 timeout 并高优播报。
3. 同一 sessionId 的迁移串行处理，乱序事件按事件时间戳补正，无法补正的标记 anomaly。
4. 状态回跳防护。completed 之后不允许直接迁回 running，只能新建任务实例或显式重试。

**功能需求**

| 编号 | 需求描述 | 业务规则 | 验收标准 |

│    ③ 语音播报引擎      ④ MCP 集成层（Server + Client）          │
├─────────────────────────────────────────────────────────────┤

### 8.2 关键数据流

**流 A：状态事件主链路**

1. 适配器从工具侧取数（会话文件、进程事件、MCP 回调、本地 API）。
2. 适配器把原始信号映射为标准事件（含 sessionId、toolId、eventType、ts、meta）。
3. 状态机引擎校验迁移合法性，写入事件日志，产出状态迁移记录。
4. 迁移记录同步三路：UI 经 WebSocket 推送；播报引擎按规则路由；MCP Server 可被外部查询。

**流 B：扫描链路**

扫描触发（首启 / 手动 / 定时）→ 遍历适配器注册表的探测规则 → 三层探测结果合并 → 更新工具清单 → 新工具出现事件（默认不播报）。

**流 C：MCP 双向链路**

外向：AI 工具经 MCP 调用 list_sessions / update_task_state → MCP Server → 状态机/查询服务。
内向：外部 MCP Server 被 Client 连接 → 工具枚举入画像 → 其调用结果可注入状态事件。

### 8.3 事件模型（标准事件 Schema）

```json
{
  "eventId": "evt_01J...",
  "sessionId": "claude-code:proj-a:sess-123",
  "toolId": "claude-code",
  "eventType": "task.waiting_human",
  "occurredAt": "2026-10-19T22:31:05+08:00",
  "actor": "tool",
  "payload": {
    "taskTitle": "重构登录模块",
    "reason": "需要授权执行 shell 命令",
    "heartbeatSeq": 42
  },
  "schemaVersion": 1
}
```

事件类型枚举（7 类）：task.started、task.waiting_human、human.responded、task.failed、task.completed、task.retried、task.archived。补充：heartbeat.lost、tool.detected、anomaly。

### 8.4 数据模型（核心表）

| 表 | 关键字段 | 说明 |
|----|----------|------|
| tools | tool_id、name、adapter_id、detect_status、version、config_path、first_seen | 工具清单 |
| sessions | session_id、tool_id、project、title、current_state、started_at、ended_at | 会话 |
| state_events | event_id、session_id、event_type、prev_state、next_state、actor、ts、payload(JSON) | 事件日志（只追加） |
| voice_rules | scope(tool/event)、action(mute/notify/speak)、template、priority | 播报规则 |
| mcp_servers | server_id、name、transport、command/url、status、tools(JSON) | 外部 MCP Server |
| audit_log | ts、actor、action、target、result | 审计 |

关系：tools 1—N sessions 1—N state_events。事件表只追加不更新，状态以 latest 迁移视图冗余一份便于查询。

## 九、关键技术选型

### 9.1 选型对比与推荐

| 层 | 方案 A（推荐） | 方案 B | 取舍理由 |
|----|---------------|--------|----------|
| 桌面壳 | Electron 28+ | Tauri 2（Rust） | A 单语言栈迭代快，MCP TS SDK 最成熟，系统托盘/通知生态齐。B 体积小内存省，但双语言维护成本高。MVP 选 A，M3 复评是否值得迁移 |
| 主语言 | TypeScript（Node + 渲染进程） | Go / Rust | MCP 官方 TS SDK 成熟；适配器生态贡献门槛低。与 spec-workflow-mcp（TS）技术路线一致，与 magpie（Go）机制路线一致 |
| 状态机 | XState v5 | 自研 FSM | XState 提供可视化与测试工具，状态图即文档。状态数少（7 态）自研亦可，但 XState 的 actor 模型利于多会话并发 |
| 本地存储 | SQLite（better-sqlite3）+ Drizzle ORM | 纯 JSON 文件 | 事件量大（多工具并行）需索引查询。关键配置另存 JSON 快照便于人读与备份（吸收 spec-workflow 文件可读优点） |
| UI | React 18 + TypeScript + Tailwind CSS | Vue 3 + Element Plus | 两案均可用，按团队栈定。推荐 React + Tailwind（组件生态与 Electron 集成样例多）。若团队 Vue 栈更熟，Vue 3 + Element Plus 等价 |
| 实时推送 | WebSocket（本地环回） | SSE | 双向（UI 可下发暂停播报等指令）故选 WebSocket |
| TTS | 平台原生优先（macOS `say`/AVSpeechSynthesizer、Windows SAPI、Linux espeak-ng）+ 可插拔云端/本地模型（piper） | 单一云 TTS | 原生零延迟零出网，符合本地优先。音色不足时插件式补 piper 本地模型 |
| MCP 实现 | @modelcontextprotocol/sdk（stdio + streamable-http） | 自研协议解析 | 官方 SDK 支持 Server 与 Client 双角色，Schema 校验内建 |
| 进程/文件监控 | Node child_process + fs.watch（macOS FSEvents）/ chokidar | 轮询 | 事件驱动降低空转 CPU |
| 打包分发 | electron-builder（mac 签名公证 / win 签名） | 平台各自打包 | magpie 的签名公证实践提示 macOS 分发必备 |
| 测试 | Vitest（单元）+ Playwright（UI 冒烟）+ 适配器契约测试 | — | 适配器契约测试保证第三方适配器输入输出合规 |

### 9.2 适配器描述包（关键技术约定）

```yaml
id: claude-code
detect:
  configPaths:
    - mac: "~/.claude/settings.json"
      envOverride: ["CLAUDE_CONFIG_DIR"]
  processNames: ["claude"]
  apis: []
sessionSource:
  type: jsonl
  pathPattern: "~/.claude/projects/**/*.jsonl"
eventMapping:
  waiting_human: { match: "permission_request", reason: "tool_approval" }
  completed: { match: "result", ok: true }
heartbeat: { intervalSec: 30, probe: "file_mtime" }
mcp:
  clientConfigFormat: "claude-code"
```

约定要点：核心引擎不出现任何具体工具名；新增工具等价于新增一份描述包；描述包经校验器（M3 起）验证路径与映射完整性。

## 十、用户交互流程

### 10.1 首次启动流程

1. 欢迎页，说明产品用途与本地优先原则，列明将读取的路径类别。
2. 授权与扫描范围确认（默认最小集，可展开高级）。
3. 扫描执行，进度展示（探测层逐项点亮）。
4. 结果页：识别到的工具卡片（名称、图标、版本、状态）+ 未识别提示 + 手动添加入口。
5. 语音测试向导（选音色、试听、设定免打扰时段）。
6. 生成 MCP 接入配置，引导粘贴到常用 AI 工具。
7. 进入主看板。

### 10.2 日常主流程

```
常驻菜单栏（状态圆点：绿=无待办 / 红=N 个待介入）
   │
   ├─ 打开主窗口 → 工具总览 → 点工具卡 → 该工具会话列表
   │                                  └→ 任务详情（时间线 / 错误 / 快捷打开）
   ├─ 待介入提醒（语音 + 系统通知）→ 点通知直达任务详情 → 「在工具中打开」
   └─ 设置 → 播报规则 / 扫描 / 隐私 / 适配器
```

### 10.3 关键页面线框思路

**页面 1：工具总览**
- 顶部：全局状态条（待介入 N / 执行中 M / 今日完成 K）+ 手动扫描按钮 + 静音开关。
- 内容区：工具卡片网格。每卡含图标、名称、版本、运行状态点、活跃会话数、最近事件时间。
- 空态：识别引导 + 「重新扫描」+ 手动添加。

**页面 2：会话看板**
- 视图切换：看板（四列：待介入 / 执行中 / 失败 / 完成）/ 列表（时间倒序）。
- 卡片信息：任务标题、来源工具、状态徽标、进入该态的时长、摘要行。
- 待介入列置顶且红框，卡上有「在工具中打开」主按钮。

**页面 3：任务详情抽屉**
- 上部：标题、来源、项目路径、当前状态、开始时间。
- 中部：状态时间线（垂直轴，节点为迁移，含触发与原因）。
- 下部：错误摘要（失败时）、快捷操作（重试引导、复制事件 JSON、静音此任务）。

**页面 4：语音与规则设置**
- 左侧规则表：事件类型 × 动作（静音 / 仅通知 / 播报）矩阵。
- 右侧试听与参数：音色、语速、音量、模板编辑、优先级说明。

### 10.4 交互原则落地

| 原则 | 落地方式 |
|------|----------|
| 状态完整 | 每页含空态、加载、错误、无权限四态；扫描失败给出修复建议 |
| 反馈及时 | 每次操作出 toast 或内联结果；播报触发时菜单栏图标闪动 |
| 操作可逆 | 忽略工具、清空历史、改规则均支持撤销（10 秒） |
| 一致性 | 状态徽标全产品统一四色四图标（橙=待介入、蓝=执行中、绿=完成、红=失败） |
| 容错引导 | 适配器加载失败指明具体文件与修复路径，不只报红 |
| 无障碍 | 全键盘可达、读屏标签完整、状态不单靠颜色区分 |

## 十一、语音播报机制

### 11.1 机制总览

```
状态迁移事件 → 播报规则引擎（匹配 scope + action）
      → 去抖与合并器（30s 去重 / 同类合并）
      → 优先级队列（高可打断，中低排队）
      → 文本渲染（模板 + 变量替换 + 长度截断 ≤ 40 字）
      → TTS 后端抽象（平台原生 / piper / 云端可选）
      → 音频输出 + 菜单栏视觉联动 + 系统通知备份
```

### 11.2 事件播报映射表（默认策略）

| 事件 | 默认动作 | 默认文案模板 | 优先级 | 可打断 |
|------|----------|--------------|--------|--------|
| task.started | 静默 | （仅通知中心） | 低 | 否 |
| task.waiting_human | 播报 | 「{tool} 需要你确认，{title}」 | 高 | 是 |
| task.failed | 播报 | 「{tool} 任务失败，{title}」 | 高 | 是 |
| task.completed | 播报 | 「{tool} 任务完成，{title}」 | 中 | 否 |
| task.timeout | 播报 | 「{tool} 长时间无响应，{title}」 | 高 | 是 |
| heartbeat.lost | 仅通知 | 「{tool} 信号丢失」 | 中 | 否 |
| tool.detected | 静默 | 「发现新工具 {tool}」 | 低 | 否 |
| anomaly | 仅通知 | 「状态异常，请查看」 | 中 | 否 |

设计要点。等待人工介入是最高价值信号，给予打断权。完成类播报不打断当前播报，避免吵扰。task.started 默认静默是防止「开始刷屏」，可在规则中开启。

### 11.3 节流、合并与免打扰

| 机制 | 规则 |
|------|------|
| 去重 | 同 sessionId + 同事件类型 30 秒内只播报 1 次 |
| 合并 | 5 分钟窗口内同工具 ≥3 个 completed 合并为「{tool} 完成了 N 个任务」 |
| 冷却 | 全局播报冷却 2 秒，防止队列积压时连续出声 |
| 免打扰时段 | 用户配置（如 22:30 到 08:30），期间仅落通知中心。waiting_human 可设「仍要出声」例外 |
| 全局静音 | 菜单栏一键静音，状态圆点仍闪烁 |
| 按工具静音 | 工具卡片与设置页均可静音单个工具 |

### 11.4 TTS 后端抽象

| 后端 | 平台 | 特点 | 适用 |
|------|------|------|------|
| macOS say / AVSpeech | macOS | 零延迟、离线、系统音色 | 默认首选 |
| SAPI.SpVoice | Windows | 系统自带、可调音色 | 默认首选 |
| espeak-ng | Linux | 轻量离线 | 默认首选 |
| piper（本地模型） | 跨平台 | 音质好、CPU 可控 | 可选增强 |
| 云端 TTS 插件 | 跨平台 | 音色丰富 | 可选，需用户显式开启且明示出网 |

统一接口：`speak(text, priority, interruptible, voiceProfile)`。后端选择失败自动降级到下一级，降级事件记入审计但不播报。

### 11.5 播报与视觉的多通道协同

语音不是唯一通道。任何播报事件同步三路：菜单栏图标状态变化、系统原生通知（含操作按钮「打开工具」「静音此任务」、通知中心留存）。语音关闭时这三路仍然生效，保证可及性。

## 十五、附录

### 15.1 用户故事（核心闭环）

1. 作为多工具开发者，我想要一眼看到本机所有 AI 工具的运行状态，以便不用逐个切换窗口确认。
   验收：Given 同时装有 3 个 AI 工具，When 打开工具总览，Then 一屏可见 3 张卡及各自运行状态。
2. 作为并行跑长任务的用户，我想要在任务等我确认时立刻被语音叫到，以便不耽误任务推进。
   验收：Given 某任务进入待人工介入，When 播报开启，Then 3 秒内听到「工具名 + 需要你确认」并有系统通知可点。
3. 作为失败敏感的用户，我想要任务失败时高优播报并直达错误详情，以便快速定位。
   验收：Given 任务失败，When 播报触发，Then 可打断当前播报且通知点击直达错误摘要。
4. 作为 AI 工具使用者，我想要让任意 AI 工具经 MCP 查到我当前的任务状态，以便在对话中直接询问「我有几个任务在等确认」。
   验收：Given AgentCue 的 MCP 已接入 Claude Code，When 对话中询问，Then 返回待介入任务数量与列表。

### 15.3 名词与术语

| 术语 | 定义 |
|------|------|
| 适配器（Adapter） | 描述某个 AI 工具的探测规则、会话源与事件映射的配置包 |
| 标准事件 | 各工具原始信号归一后的 7 类任务生命周期事件 |
| 待人工介入（waiting_human） | 任务需要用户确认、授权或补充输入的状态 |
| MCP | Model Context Protocol，模型上下文协议，用于 AI 工具与外部能力的标准接入协议 |
| 心跳（heartbeat） | 适配器周期性确认工具仍在工作的信号，用于超时判定 |
